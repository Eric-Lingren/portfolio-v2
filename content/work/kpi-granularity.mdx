## Context

At Standard Metrics, investment firms collect financial and operating data from their portfolio companies through Information Requests. A firm picks the KPIs it wants, picks the companies, and sends the request. Each company fills in its numbers.

Until this project, a request had one reporting cadence. Every KPI in it was asked for monthly, or every KPI was asked for quarterly. [ERIC: confirm the stack list above matches what you actually touched, including the API layer.]

## Problem

Real portfolio data does not arrive on one schedule. A firm might want Net Burn monthly, revenue quarterly, and a headcount figure once a year. With a single cadence per request, the only way to get that was to send several requests to the same company, and the firm had to manage each one separately.

The effect was most obvious for firms with large portfolios. One firm had to create 84 separate Q3 requests, one per company, because the cadence settings could not vary by KPI or by company. Companies received more emails than they needed, and the firm did more setup work every reporting period. ## Key decisions

**Granularity belongs to the KPI, not the request.** The first design question was where the setting should live. Putting it on the request kept the data model simple but left the original problem in place. I moved it to the individual KPI inside a request, which meant the configure page, the validation, and the way companies see their asks all had to understand a cadence per KPI. [ERIC: describe the data model change in one or two sentences, in your own words.]

**Ship in phases.** Phase 1 covered per-KPI granularity for the firm's standard metrics. Phase 2 added company-specific metrics, which had their own flow through the request and needed separate work.

Splitting them let firms start using the main feature while the harder case was still in design. [ERIC: was this split your call, or agreed with product? Say which.]

**Make bulk the default path.** The feature touches many KPIs across many companies at once, so I built a bulk endpoint for setting granularity instead of one call per KPI. That kept the configure page responsive for large portfolios. [ERIC: add one concrete detail about the bulk endpoint, such as how it handles partial failure.]

**Remember what the firm chose.** Early users were re-entering the same cadences every quarter. A follow-on change made the settings carry forward into the next request. ## Impact

After Phase 2, a firm could send one request with different cadences per KPI, where before it needed a separate request for each cadence. Before Phase 2, one firm needed 84 separate Q3 requests. Afterward, over 20 Q3 requests went out with Net Burn switched from monthly to quarterly.

Adoption showed up quickly after Phase 1: of 75 Q3 requests, 24 had changed granularities from the default. User acceptance testing, internal and external, passed with one rare bug.

## What I'd do next

The cadence settings are still configured one request at a time. I would add firm-level defaults, so a firm sets Net Burn to monthly once and every new request starts there. [ERIC: is this what you would actually do, or is there a different next step?]

I would also show companies why a KPI is asked at a given cadence. Right now they see the ask but not the reasoning. [ERIC: replace with the real gap you saw, if different.]

Finally, I would add reporting on which cadences firms actually use, so the defaults can be based on data instead of guesses. [ERIC: confirm or cut.]
