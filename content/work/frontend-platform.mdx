## Context

Standard Metrics is a portfolio monitoring product for investment firms. By early 2026 the frontend had grown for several years across a large team, and the code showed it. [ERIC: one sentence on team size and how many engineers touched the frontend, if you want that scale stated.]

## Problem

Three separate folders held UI components, and each had its own conventions. A button could exist in all three with slightly different props. New engineers had to learn which folder was "current" by asking someone, and imports crossed folder lines in every direction.

The test setup had the same shape. Jest ran the suite, a newer part of the codebase wanted Vitest, and the two did not share configuration. Page layout was split too. The portfolio-company pages carried their own legacy layout code that no longer matched the rest of the app.

None of this broke anything on a given day. It slowed every change slightly and made each change a little riskier. [ERIC: any concrete incident or recurring complaint that made this worth funding, with no customer or colleague names.]

## My role

I led the migration and broke it into seven steps so each one could ship on its own. I wrote the plan, did most of the implementation on the hardest steps, and reviewed the rest. I also wrote the release note at each step so other teams knew what changed for them. ## Key decisions

**One component tree, built on shadcn primitives.** Instead of picking a winner among the three folders, I moved everything into a single component tree and built the shared primitives on shadcn. Owning the primitive code meant we could adjust behavior without waiting on a library release. [ERIC: why shadcn over the existing in-house components, in your words.]

**Rewrite imports with a codemod, in one pull request.** Hand-editing imports across the codebase would have produced a long-lived branch that conflicted with everyone. A tested codemod rewrote 1,853 imports across 1,046 files in a single PR, so the repo was never in a half-moved state for long. The count matters only as scale: it is why a codemod, and not a checklist, was the right tool. [ERIC: how you tested the codemod before running it on the whole repo.]

**Lint rules enforce the boundaries.** A folder move decays unless something stops people from undoing it. I added lint rules that reject imports from the old locations and block cross-module reach-ins, so the structure is checked in CI rather than remembered. [ERIC: which rules, and whether any of them caught a real mistake after the migration.]

**Cut over the portfolio-company pages last.** The new shell replaced the legacy layout only after the component tree was stable. The topbar cutover moved eight routes to per-tab containers and deleted about 1,450 lines of legacy layout code. Doing it last meant the shell was built from the new components from day one.

**Move tests to Vitest.** I moved the suite from Jest to Vitest and then upgraded to v4. I am not claiming any speed result for this work, because the test-speed improvements posted around the same time came from separate work by someone else. The reason for the move was one runner and one configuration for the whole codebase.

## Impact

The codebase now has one place for UI components, one test runner, and a lint-enforced rule about where code may import from. The portfolio-company pages run on a single shell, and experiences are organized into modules.

My release note for the final step said the result was faster onboarding, fewer broken imports, and less wasted dev time. That is the intent, not a measurement. ## What I'd do next

The folder structure is settled, but the primitives are not documented as well as they should be. A short contribution guide with an example for each primitive would finish the job, because the lint rules say what is not allowed and say nothing about what to do instead.

I would also measure the thing I could not. Tracking import-related failures and time to first merged change would turn the "faster onboarding" claim into data. [ERIC: anything else you would change, or that surprised you.]
