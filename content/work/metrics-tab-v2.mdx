## Context

Standard Metrics is a portfolio monitoring product for investment firms. The Metrics Tab is where a firm sees the numbers its portfolio companies report, one company at a time, laid out as a grid of metrics over reporting periods. Finance analysts and finance leads work in it day to day.

The first version of the tab let people edit numbers, but it was cumbersome, laggy, and it had no keyboard interactions beyond tab. Metrics Tab v2 rebuilt it as a workspace where people could change the numbers in place, the way they already do in a spreadsheet.

## Problem

People who work with financial data already know how a spreadsheet behaves. They expect arrow keys to move between cells, a double-click or a keystroke to start editing, and a paste from Excel to land where they put it. A grid that looks like a spreadsheet but does not behave like one feels broken, even when every feature technically works.

The old tab did not meet that quality bar. Every edit took more clicks than it should, and none of the keyboard habits people rely on worked.

The rebuild also had to keep what already worked. The old tab could open the Detailed Datum Tracer, which shows an audit trail of where a number came from. The new grid had to support it from any cell, without getting in the way of editing.

## My role

Four engineers worked on the rebuild, including me, with a product manager. I owned every keyboard interaction in the grid. That covered arrow keys, Tab and Enter, editing inside a cell, cut, copy and paste for single cells and bulk selections, and interactions inside nested cells for dropdowns, etc.

## Key decisions

**One state machine for every interaction.** Keyboard, mouse, editing and paste all change the same few things: which cell is selected, whether it is being edited, and what value it holds. I put those transitions in a single reducer-driven state machine instead of spreading them across event handlers. Each input becomes an action, and the reducer decides what happens next. There were a lot of edge cases, and pressing Escape mid-edit caused the most surprises. With every transition in one place, each case could be reproduced and fixed on its own.

**Match spreadsheet habits, not a custom model.** Click selects a cell. Double-click or typing starts an edit. Delete in select mode clears the value. Arrow keys, Tab and Enter move the selection. We copied Excel's most intuitive keyboard behavior as closely as we could, so there was nothing new to learn.

**Paste from Excel as a first-class path.** Many people keep their numbers in a spreadsheet first. Paste had to take a block copied from Excel and place it across the right cells, not drop it all into one. Cut, copy and paste work the same way on a bulk selection. A paste larger than the grid is truncated to fit.

**Edit in the reporting currency.** A firm often looks at companies that report in different currencies. The grid shows and edits values in the reporting currency, so the numbers on screen match what the firm compares. If the firm picks a different currency on that page, edits follow that choice.

**Ship the core loop first.** We built one complete editing workflow, from selecting a cell to saving a change, before adding anything else. That loop was enough to start the beta.

## Impact

The beta reached 35 users across 11 firms. At one beta firm, some users made the new tab their primary workspace before it had even launched. After the beta, the new Metrics Tab went live for all customers.

## What I'd do next

There were a lot of edge cases, and most of them came up during the build. If I did it again, I'd start with a table: every key, in select mode and edit mode, with the expected result. Each row becomes a test, so the gaps show up before the code does.

I would also put undo in the first release. It shipped later, as a follow-on. In a grid where people edit financial numbers, Ctrl+Z is a safety net, not a nice-to-have. Every edit already passed through one reducer, which is a natural place to keep that history.
